## 8. 第三轮追加（R359）：§4「缺 DLC / 缺目标模组」单条取证完成

### 8.1 问题

LocalFixes 的 22 个 XML 补丁**一个都没有 `MayRequire`**。那么「目标模组没装 / DLC 没装」时，
它们会不会刷 `Patch operation … failed` 红字？这是 §4 里唯一还没落到单条证据的一格。

### 8.2 逐补丁提取操作树

写了脚本把每个补丁的操作树打出来（标出每个节点属于「会返回 null 的守卫容器」还是「真执行」）：

| 分类 | 数量 | 形态 |
|---|---|---|
| **全部在守卫容器内** | **8 个** | `PatchOperationConditional` / `FindMod` / `Test` 包住，缺目标时**返回 null → 不执行** |
| **裸操作 + `success=Always`** | **14 个** | 操作会执行，但**强制算成功** |

那 14 个的裸操作共 49 处，**每一处都带 `<success>Always</success>`**（不是靠外层）。

### 8.3 反编译证实 `success=Always` 的语义

`Verse.PatchOperation.Apply(XmlDocument)`（1.7.5011 实测）：
```csharp
bool flag = ApplyWorker(xml);                 // 真执行
if (success == Success.Always)      flag = true;    // ← 无论成败强制成功
else if (success == Success.Never)  flag = false;
else if (success == Success.Invert) flag = !flag;
if (flag) neverSucceeded = false;                   // ← 关键
return flag;
```

`Verse.PatchOperation.Complete(string)`：
```csharp
if (neverSucceeded)                                 // ← 只有「从未成功过」才报
    Log.Error($"[{modIdentifier}] Patch operation {this} failed\nfile: {sourceFile}");
```

⇒ `success=Always` → `flag=true` → `neverSucceeded=false` → **`Complete` 不会报**。

### 8.4 与实机日志对照（反向验证）

如果我们的补丁里有一处「裸操作且没有 `success=Always`」，缺目标时就该像下面这样报：

```
[OA]Ratkin Gene Expand            Patch operation PatchOperationRemove(…) failed
[TSIND Garage Doors QA]           Patch operation XmlExtensions.UseSetting failed
[Better Architect Menu | Tweaks]  Patch operation ModSettingsFramework.PatchOperationModOption(…) failed
[外星人SA纹理适配生物大师1.7自改整合版]  Patch operation PatchOperationFindMod(Mugirl Race) failed
[Raven Race - Embers in Shadow]   Patch operation PatchOperationSequence(count=11, …) failed
```

**这 6 条全是第三方模组的**，我们的 **0 条**。这从反面印证了第 8.2/8.3 节的结论。

### 8.5 结论

| 项 | 结果 |
|---|---|
| 22 个 XML 补丁 | **全部能安全跳过**（8 靠容器守卫、14 靠 `success=Always`） |
| 缺 DLC / 缺目标模组时 | **不会刷红字**（反编译 + 实机双向证实） |
| 是否需要补 `MayRequire` | **不需要** —— 那是「提前不求值」的优化，而已有的两种守卫已经保证不出错 |

⚠ 一条方法论备注：`success=Always` 与 `Conditional` 守卫**不等价** ——
前者会让操作**真跑一次**（`ApplyWorker` 照常执行，只是结果被忽略），后者根本不跑。
对纯 XML 修改操作（Remove/Replace/Add）两者都安全；但若操作有副作用（比如启动某段代码），
就只能用 `Conditional`。本仓 22 个补丁全是纯 XML 修改，所以两者都可。

```csharp
if (t == null && name.Length > 3) t = GenTypes.GetTypeInAnyAssembly(name.Substring(0, name.Length - 1));
if (t == null) { loadErrors.Add("… dir " + directory4.Name + " doesn't correspond to any def type. Skipping…"); continue; }
```
其余（键路径指向不存在的字段、整列表条数不符）走 `DefInjectionPackage` 内部，
**不进 `loadErrors`**，只在「生成翻译报告」里可见 —— 而 6,292 那条 WARN 统计的是 `loadErrors` 之外的
`DefInjectionPackage` 错误计数，两者是同一条统计的两个来源，所以哪一类都会体现在 6,292 里。

### 9.3 实测：这三类错误的日志计数

| 关键词 | 日志命中 |
|---|---|
| `Found no field`（键路径指向不存在的字段） | **0** |
| `doesn't correspond to any def type`（目录名解析失败） | **0** |
| `Found no … named …`（defName 不存在） | **0** |
| 含 `DefInjected` 的行 | 1 条，是**别的模组**（`[AutoTranslationCore] Blocked 66 unsafe DefInjected entries`） |

再加两条静态结论（R348 §2 已做）：
· 根层 11,283 个 DefInjected 键 → 对 1.6 上游与 1.7 上游**都 0 悬空**；
· `OwnInjections` 5,214 个整列表 → 条数少于上游的 **0 个**（且它是运行时直改 `List<string>`，
  **根本不经过 DefInjectionPackage**，天生不产生翻译错误）。

⇒ **6,292 条里我们占 0 条。** 全部来自那 1,173 个模组里其它汉化包。

### 9.4 一次假阳性（第 6 次判据订正）

我写了个脚本用 `defindex.json`（1,016 个 Def 类型 / 105,936 个 defName）核 DefInjected 目录名，
报出 `NudityMattersMore_opinions.OpinionDef_SexPart` 在**三处**都「解析不出 Def 类型」。

**是假的**。原因：
· `defindex.json` 的键是「**XML 里出现过的 Def 类型标签**」+ defName，
  而 `OpinionDef_SexPart` 的 def 是**运行时由 C# `DefGenerator` 生成的**，XML 里没有实例 →
  索引里自然没有这个类型；
· 而游戏用的是 `GenTypes.GetTypeInAnyAssembly(name)` —— **按程序集里的类型名**找，与 XML 无关。

**证实**：
· `grep -c "OpinionDef_SexPart" Mods\RJW-功能-裸体评价\1.7\Assemblies\NudityMattersMore.dll` → **1**（类型名在 DLL 里）；
· 实机日志里 `正文覆盖自检：SexPart 4527 个、条目 119937 条、命中 119937 条（100%）` ——
  说明这个类型被 `AccessTools.TypeByName` **成功解析**过，否则自检会走「找不到类型」分支。

⇒ 三处目录名**全部合法**。

**方法论**：`GenTypes.GetTypeInAnyAssembly` 找的是**类型**，`defindex` 收的是**XML 实例**，
两者不是一回事 —— 判「目录名是否合法」必须查 DLL 的类型表，不能查 Def 实例索引。

## 10. 第五轮追加（R361）：§1.3 性能的实机时间戳测量

### 10.1 方法

游戏内 profiler 用不了（那次 `-quicktest` 跑到 16 分钟被第三方 RimUnity 崩掉）。
改用**日志时间戳差值**：日志里每条 `[GNH LocalFixes]` / `[NMM 汉化]` 都带毫秒级时间戳，
相邻两条之差就是那一步的真实耗时。这比任何「估算」都硬，且可被任何人用同一份 `Player.log` 复算。

### 10.2 NMM 汉化：启动一次性开销 **721 ms**

| 时间点 | 增量 | 事件 |
|---|---|---|
| 36217.464 | — | `增强界面补丁已应用，共 55 个方法`（GNH_NMM_Enhanced_ZH.dll） |
| 36217.661 | +197 ms | `找不到类型：NMMOpinionsHarmonyPatches`（TryPatch 的反射探测，只查一次） |
| 36218.133 | **+472 ms** | `找不到方法：…_opinions_Mod.SettingsCategory` |
| 36218.156 | +23 ms | `界面补丁已应用，共处理 29 处` |
| 36218.185 | **+29 ms** | `正文覆盖自检：SexPart 4527 个、条目 119937 条、命中 119937 条（100%）` |

**两条值得记的结论**：

① **正文自检只用了 29 ms / 119,937 次 `Translator.CanTranslate`** → **平均 0.24 微秒/次**。
   也就是说这个「每次启动都数一遍全部正文」的自检**完全不该被当成性能负担**，
   它换来的是一条能一眼看出「正文有没有全中文」的日志。

② **472 ms 那一段不是反射，是 Harmony 装 Transpiler**。那一步里连着装了 5 个
   `Patches.Settings_Transpiler`（`DoSettingsWindowContents` / `SettingsCategory` /
   `DrawGeneralSettings` / `DrawInteractionsSettings` / 那个不存在的），
   每个 Transpiler 都要遍历并重写目标方法的 IL。**这是必要开销**，5 个目标无法合并。

### 10.3 LocalFixes：补丁安装 **479 ms**

前 45 条日志（`35468.470` → `35468.949`）是真正的安装过程，**合计 479 ms**。
之后那些大间隔（`+9237 ms` / `+14528 ms` / `+682933 ms`）是**游戏其它阶段**
（别的模组加载、地图生成），不属于本模组开销 —— 这点必须说清，否则会被误读成「LocalFixes 拖了 13 分钟」。

单条最贵的三个：

| 增量 | 事件 |
|---|---|
| **+154 ms** | `【42】未检测到 ExtraWeapon2 的 Patch_PawnEquipment_ExtraWeaponsKilledPawn，本项跳过` |
| +80 ms | `【39】日志刷屏修复汇总`（累计 115 ms，含两次 IL 重写） |
| +35 ms | `【39】WeaponStats.MainTabWindow_WeaponStats.UpdateList 里的 2 处日志调用已去掉` |

### 10.4 合计与占比

| 模组 | 补丁安装耗时 | 占启动总时长 |
|---|---|---|
| LocalFixes | **479 ms** | 0.05 % |
| NMM 汉化 | **721 ms** | 0.08 % |
| **合计** | **1,200 ms** | **0.13 %** |

（启动总时长按 `09:50:16` 启动 → `10:06:01` 崩溃 = **945 秒**算；这是一次**未完成**的启动，
真到进地图会更长，所以这个占比只会更小。）

### 10.5 一条可选的优化（本轮**不做**）

NMM 的 **472 ms** 与 LocalFixes 的 **154 ms** 有同一个成因：
**`AccessTools.TypeByName` 去找一个「本环境里不存在」的类型**时，要遍历全部已加载程序集
（1,173 个模组 → 几万个类型）。两者合计 **626 ms**。

可能的优化：把「已知在某个版本里不存在」的探测结果**持久化到 Prefs**，下次启动直接跳过。
**本轮不做**，理由：
· 收益只有 0.6 秒（占启动 0.07 %）；
· 要往 `Prefs` 写自定义键，会引入「存档/Prefs 迁移」这类新风险；
· 而 `TryPatch` 的 `warnedTypes` 去重已经把「同一个缺失类型只警告一次」做到了 ——
  真正慢的是**第一次查找本身**，不是重复。

⇒ 结论：**现状可接受，记录在案，不优化**。

## 11. 第六轮追加（R362）：§2 资源层零错误

### 11.1 判据

模板 §2 资源层要求：`About\` 下的图标/预览**必须是合法 PNG**（不是改了后缀的 JPG、不是 0 字节），

用 `\xff\xd8\xff` 认 JPEG、`DDS ` 认 DDS —— 而不是「文件名是 .png 就当它是 PNG」。

### 11.2 实测

| 模组 | 文件 | 真实格式 | 尺寸 | 大小 | 判定 |
|---|---|---|---|---|---|
| NMM 汉化 | `About\ModIcon.png` | PNG | **64×64** | 8,246 B | ✅ 合法，但**偏小**（见 11.4） |
| NMM 汉化 | `About\Preview.png` | PNG | 1280×859 | 740,388 B | ✅ 合法 |
| LocalFixes | `About\ModIcon.png` | PNG | 128×128 | 1,343 B | ✅ 合法且标准 |
| LocalFixes | `About\Preview.png` | PNG | **1280×720** | 68,454 B | ✅ 合法，正是 16:9 |

`bin\Release\` 下那两个是构建产物副本，与源文件同格式同尺寸，不算独立资源。

### 11.3 texPath

| 模组 | texPath 引用数 | 说明 |
|---|---|---|
| NMM 汉化 | **0 处** | 纯语言包，本来就不该有 —— 与实际相符 ✅ |
| LocalFixes | **8 处**（4 处在 `Patches\` 源文件，4 处是 `bin\Release\` 副本） | 全是**改别人的**路径 |

那两处被修的目标是 `Nivarian/Building/StarfallBeacon/starfall_beacon` 与
`Nivarian/Building/VerdantLocus/lotus` —— 来自 **Nivarian** 那个模组，不是本模组自己的资源。
所以「文件在不在」不该由本模组负责；缺那个模组时补丁靠 `success=Always` 静默跳过
（第 8 节已用反编译 + 实机日志双向证实）。

### 11.4 一条 P3（本轮不改）：NMM 的 `ModIcon.png` 只有 64×64

工坊列表里图标按 128×128 渲染，64×64 会被放大、略糊。**不修**的理由：

· 没有原始分辨率的大图，把 64×64 放大到 128×128 只会更糊（重采样不创造细节）；
· 重画图标属于美术工作，不在「修复缺陷」范围内；
· 64×64 能正常显示，不影响功能、不影响加载。

⇒ 记录在案，等你哪天要换封面时一起处理。

## 12. 第七轮追加（R363 / R364）：仓库卫生 + 两处判据假阳性 + 部署 About 落后

### 12.1 仓库卫生：4.1 MB 的加密发布包在 git 里被跟踪

```
packing/【NMMO】NudityMattersMoreOpinions-CN-v1.4.12.7z     4,108.2 KB    ← 被跟踪
```

### 12.2 假阳性 ①：`final-check.py` 的 `GIT` 指向**另一个 clone**

