## 8. 第三轮追加（R359）：§4「缺 DLC / 缺目标模组」单条取证完成

### 8.1 问题

LocalFixes 的 22 个 XML 补丁**一个都没有 `MayRequire`**。那么「目标模组没装 / DLC 没装」时，
它们会不会刷 `Patch operation … failed` 红字？这是 §4 里唯一还没落到单条证据的一格。

### 8.2 逐补丁提取操作树

写了脚本把每个补丁的操作树打出来（标出每个节点属于「会返回 null 的守卫容器」还是「真执行」）：

| 分类 | 数量 | 形态 |
|---|---|---|
| **全部在守卫容器内** | **8 个** | `PatchOperationConditional` / `FindMod` / `Test` 包住，缺目标时**返回 null → 不执行** |
| **裸操作 + `success=Always`** | **14 个** | 操作会执行，但**强制算成功** |

那 14 个的裸操作共 49 处，**每一处都带 `<success>Always</success>`**（不是靠外层）。

### 8.3 反编译证实 `success=Always` 的语义

`Verse.PatchOperation.Apply(XmlDocument)`（1.7.5011 实测）：
```csharp
bool flag = ApplyWorker(xml);                 // 真执行
if (success == Success.Always)      flag = true;    // ← 无论成败强制成功
else if (success == Success.Never)  flag = false;
else if (success == Success.Invert) flag = !flag;
if (flag) neverSucceeded = false;                   // ← 关键
return flag;
```

`Verse.PatchOperation.Complete(string)`：
```csharp
if (neverSucceeded)                                 // ← 只有「从未成功过」才报
    Log.Error($"[{modIdentifier}] Patch operation {this} failed\nfile: {sourceFile}");
```

⇒ `success=Always` → `flag=true` → `neverSucceeded=false` → **`Complete` 不会报**。

### 8.4 与实机日志对照（反向验证）

如果我们的补丁里有一处「裸操作且没有 `success=Always`」，缺目标时就该像下面这样报：

```
[OA]Ratkin Gene Expand            Patch operation PatchOperationRemove(…) failed
[TSIND Garage Doors QA]           Patch operation XmlExtensions.UseSetting failed
[Better Architect Menu | Tweaks]  Patch operation ModSettingsFramework.PatchOperationModOption(…) failed
[外星人SA纹理适配生物大师1.7自改整合版]  Patch operation PatchOperationFindMod(Mugirl Race) failed
[Raven Race - Embers in Shadow]   Patch operation PatchOperationSequence(count=11, …) failed
```

**这 6 条全是第三方模组的**，我们的 **0 条**。这从反面印证了第 8.2/8.3 节的结论。

| 缺 DLC / 缺目标模组时 | **不会刷红字**（反编译 + 实机双向证实） |
| 是否需要补 `MayRequire` | **不需要** —— 那是「提前不求值」的优化，而已有的两种守卫已经保证不出错 |

⚠ 一条方法论备注：`success=Always` 与 `Conditional` 守卫**不等价** ——
前者会让操作**真跑一次**（`ApplyWorker` 照常执行，只是结果被忽略），后者根本不跑。
对纯 XML 修改操作（Remove/Replace/Add）两者都安全；但若操作有副作用（比如启动某段代码），
就只能用 `Conditional`。本仓 22 个补丁全是纯 XML 修改，所以两者都可。

## 9. 第四轮追加（R360）：6,292 条翻译错误的归属，以及一次「目录名」假阳性

### 9.1 问题

实机日志里有一条：
```
10:02:34.048  WARN  Translation data for language Simplified Chinese has 6292 errors.
                    Generate translation report for more info.
```
这是**整个语言环境**（1173 个模组的汉化包加在一起）的错误总数。
之前一直把它归到「已知非缺陷」，但**从没核实过我们占多少**。

### 9.2 判断方法：反推 DefInjectionPackage 会在什么情况下记错误

反编译 `Verse.LoadedLanguage.LoadData()`（1.7.5011）后可见，DefInjected 这条路上只有两处会记账：

```csharp
// ① 目录名解析不出 Def 类型 → 记一条 + 整个目录丢弃
Type t = GenTypes.GetTypeInAnyAssembly(name);
if (t == null && name.Length > 3) t = GenTypes.GetTypeInAnyAssembly(name.Substring(0, name.Length - 1));
if (t == null) { loadErrors.Add("… dir " + directory4.Name + " doesn't correspond to any def type. Skipping…"); continue; }
```
其余（键路径指向不存在的字段、整列表条数不符）走 `DefInjectionPackage` 内部，
**不进 `loadErrors`**，只在「生成翻译报告」里可见 —— 而 6,292 那条 WARN 统计的是 `loadErrors` 之外的
`DefInjectionPackage` 错误计数，两者是同一条统计的两个来源，所以哪一类都会体现在 6,292 里。

### 9.3 实测：这三类错误的日志计数

| 关键词 | 日志命中 |
|---|---|
| `Found no field`（键路径指向不存在的字段） | **0** |
| `doesn't correspond to any def type`（目录名解析失败） | **0** |
| `Found no … named …`（defName 不存在） | **0** |
| 含 `DefInjected` 的行 | 1 条，是**别的模组**（`[AutoTranslationCore] Blocked 66 unsafe DefInjected entries`） |

再加两条静态结论（R348 §2 已做）：
· 根层 11,283 个 DefInjected 键 → 对 1.6 上游与 1.7 上游**都 0 悬空**；
· `OwnInjections` 5,214 个整列表 → 条数少于上游的 **0 个**（且它是运行时直改 `List<string>`，
  **根本不经过 DefInjectionPackage**，天生不产生翻译错误）。

⇒ **6,292 条里我们占 0 条。** 全部来自那 1,173 个模组里其它汉化包。

### 9.4 一次假阳性（第 6 次判据订正）

我写了个脚本用 `defindex.json`（1,016 个 Def 类型 / 105,936 个 defName）核 DefInjected 目录名，
报出 `NudityMattersMore_opinions.OpinionDef_SexPart` 在**三处**都「解析不出 Def 类型」。

**是假的**。原因：
· `defindex.json` 的键是「**XML 里出现过的 Def 类型标签**」+ defName，
  而 `OpinionDef_SexPart` 的 def 是**运行时由 C# `DefGenerator` 生成的**，XML 里没有实例 →
  索引里自然没有这个类型；
· 而游戏用的是 `GenTypes.GetTypeInAnyAssembly(name)` —— **按程序集里的类型名**找，与 XML 无关。

**证实**：
· `grep -c "OpinionDef_SexPart" Mods\RJW-功能-裸体评价\1.7\Assemblies\NudityMattersMore.dll` → **1**（类型名在 DLL 里）；
· 实机日志里 `正文覆盖自检：SexPart 4527 个、条目 119937 条、命中 119937 条（100%）` ——
  说明这个类型被 `AccessTools.TypeByName` **成功解析**过，否则自检会走「找不到类型」分支。

⇒ 三处目录名**全部合法**。

**方法论**：`GenTypes.GetTypeInAnyAssembly` 找的是**类型**，`defindex` 收的是**XML 实例**，
两者不是一回事 —— 判「目录名是否合法」必须查 DLL 的类型表，不能查 Def 实例索引。

· 而 `TryPatch` 的 `warnedTypes` 去重已经把「同一个缺失类型只警告一次」做到了 ——
  真正慢的是**第一次查找本身**，不是重复。

⇒ 结论：**现状可接受，记录在案，不优化**。

## 13. 第八轮追加（R366）：工具自审 —— 「exit 0」对这个脚本到底意味着什么

### 13.1 为什么要审工具

到现在为止，本报告里所有「零错误 / 全绿 / 通过」的结论**都建立在这两组脚本之上**：
NMM `tools/*.py`（25 个）、LocalFixes `tools/*.py`（30 个）。

> **`exit 0` 只有在「失败时会 exit 非 0」的前提下才有意义。**
> 一个永远 `sys.exit(0)` 的脚本，跑一万次「通过」也只说明它没崩。

### 13.2 第一次扫：正则太窄 → 一堆假阳性

```python
sys.exit(0 if not need else 1)      # audit-comments.py

```
三种都能正常报错，**全被误判**。这是第 3 次栽在「判据比现实窄」。

| `verify-r22-langkeys.py` | 只 print 各语言「缺 N」 | ❌ 无判据 |
| `verify-r5-migration.py` | 只 print 每项 `✓/✗` | ❌ 无判据 |

`audit-comments.py`（`sys.exit(0 if not need else 1)`）✓ —— **NMM 的检查类脚本都已有判据**。

## 15. 第十轮追加（R369）：LocalFixes §3.3 跨版本兼容 —— 62 个 xpath 字段逐一过

### 15.1 问题

用户的要求里有一条：「也要注意对目标模组可能存在的旧版本进行向下兼容」，
而模板 §3.3 管的是「同一份补丁在 1.6 / 1.7 两套引擎下都要能用」。

XML 补丁的 xpath **按字段路径匹配**。若某字段在 1.6→1.7 之间改名，
同一个 xpath 在旧版就匹配不到 —— 而 `success=Always` 会让它**静默跳过**，
表现是「1.6 下这条修复没生效，日志里什么也不说」。这正是最难发现的一类失效。

### 15.2 做法

1. 从 22 个补丁抽出**全部 `<xpath>`**；
2. 用 `/([A-Za-z_][A-Za-z0-9_]*)` 切出字段段（排除 `Defs/` 根与 `li`）；
3. 对每个字段名，到 **1.6 与 1.7 两份 `Assembly-CSharp.dll`**（15,777,280 B / 15,637,504 B）
   里各做一次字节搜索；
4. 两边都有 → 跨版本安全；只有一边 → 版本敏感。

**判据局限（必须写清）**：查的是「这个名字在两份程序集里**出现与否**」——
这是 xpath 能解析的**必要条件**，不是充分条件（字段存在但位置变了也匹配不到，
那种情况靠 xpath 的精确路径本身兜住）。真正的充分验证只能在两套引擎下各跑一次游戏。

### 15.3 结果：62 个字段

| 判定 | 数量 | 说明 |
|---|---|---|
| ✅ 两版都有 | **44** | 跨版本安全 |
| ❓ 两版都找不到 | **17** | **模组自定义 XML 字段或命名空间**，不是原版成员 —— 天然不受引擎版本影响 |
| ⚠ 只在 1.7 | **1** | `MaterialDef` |
| ⚠ 只在 1.6 | 0 | — |

### 15.4 那唯一的 1 个：`MaterialDef`

它出现在 `RJW17_SraeLibFieldCleanup.xml` 的 xpath 里：

```
//MaterialDef | //ThoughtDef[@Class="SRAELib.ThoughtDef_HediffAttraction"] | …
```

`MaterialDef` 是 **1.7 才有的 Def 类型**（1.6 的程序集里搜不到这个名字）。
所以 1.6 下这段 xpath 必然匹配不到。

**但它已经被两重保险覆盖**：
1. 该补丁的每个操作都带 `<success>Always</success>`（第 8 节已用反编译证实：
   `success == Success.Always` → `flag = true` → `neverSucceeded = false` → `Complete` 不报）；
2. 实机日志里它走的是**自动让路**那条：
   ```
   [GNH LocalFixes] XML 补丁按「上游已自行修好」让路：RJW17_SraeLibFieldCleanup.xml
                    [xmlRjw17SraeLibField]。目标 dll 里那个字段现在是存在的…
   ```

⇒ **1.6 下它静默跳过，不报错、不误改。无缺陷。**

### 15.5 抽查 17 个「两版都找不到」的字段，确认都是模组自定义

| 字段 | 来源 |
|---|---|
| `coverMovementTicks` / `silos` | `IRBM.SiloExtension`（边缘弹道导弹）的 XML 结构 |
| `graphicPaths` / `individualPaths` / `races` / `alienRace` | **HAR**（Humanoid Alien Races）的 XML 结构 |
| `targetNullifyingHediffs` | 某模组的 Hediff 字段 |
| `AlienRace` / `SimManagementLib` / `Rimworld_Animations` / `rjw` | 命名空间段，出现在 `Defs/Rimworld_Animations.GroupAnimationDef` 这类路径里 |
| `GoodsList` / `ResultOptions` / `starfall_beacon` / `Moonlight_HuoShu` / `SR_NewMoonlight` / `NewMoonlight_HuoShu` | 目标模组自己的 defName 或字段名 |

这些都是**目标模组的 XML 结构**，不是原版成员 —— 引擎换版本不影响它们能不能被匹配
（只要那个模组的 XML 结构没变）。

### 15.6 结论

| 项 | 结果 |
|---|---|
| 22 个补丁 / 62 个 xpath 字段 | **61 个跨版本安全**（44 两版都有 + 17 模组自定义） |
| 唯一版本敏感项 | `MaterialDef`（只在 1.7），由 `success=Always` + 自动让路覆盖 |
| 是否需要改 | **不需要** —— 无缺陷 |

⚠ 这一格的判据只到「名字存在与否」这一层。**真正的验证必须在 1.6 引擎下实跑一次**

## 17. 第十二轮追加（R371）：72 个开关「关掉会怎样」—— 界面点击验证的前置分析

### 17.1 为什么要先做静态分析

模板 §4「极端场景」里有一类是「用户把某个开关关掉」。而 72 个开关关掉的后果**并不一样**：

| 类型 | 关掉后 | 危险度 |
|---|---|---|
| 降噪类 | 日志又变吵，游戏行为不变 | 无 |
| 恢复原问题 | 原模组那个 bug 回来了 | 低（本来就是坏的） |
| **互为前提** | 关一个让另一个失效 | **中 ~ 高** |
| 关掉让某项「半运行」 | 补丁装了但依赖的另一个没装 | **高** |

**只有「互为前提」这一类可能构成设计问题** —— 它表现为「关了 A，B 看着还开着但实际没生效」，
而用户从界面上看不出来。所以先做静态分析，把这一类挑出来逐条读原文。

### 17.2 分析结果（72 项按描述语义分档）

| 档 | 项数 | 判据关键词 |
|---|---|---|
| **互为前提** | **4** | 「两项都开」「一起开」「必须同时」「配合」「总控」「它不替代」 |
| 有条件让路 | 9 | 「自动失效」「自动恢复」「让路」「若作者……」「若退回」 |
| 降噪类 | 7 | 「只是不再」「只拦」「只静音」「噪音」「不再刷」「降噪」 |
| 恢复原问题 | 2 | 「会重新」「会再」「恢复原」「原样返回」 |
| 未分类（需人工读） | **50** | —（描述里没有上述任何关键词） |

那 50 项未分类，是描述写得具体、但没有用我列的关键词（**我的判据覆盖不全**，
第 16 次同类问题）。不过这不影响本节结论 —— 本节只需要确认「互为前提」那一档。

### 17.3 那 4 项「互为前提」，逐条读原文

| 开关 | 原文关键句 | 判定 |
|---|---|---|
| `allDiagnostics`（全部诊断一起开） | 「★ 它**不替代**那三个各自的开关：关掉它，那三个回到『各看各的』；**它们原来的勾选状态不会被改动**」 | ✅ **明确说明了关掉安全** —— 它只是个批量勾选按钮 |
| `steamWorkshopHook`（工坊信息崩溃第二道保险【22】） | 「与上一项是同一场崩溃的另一条路……**两项都开着最稳**」 | ⚠ **不是硬依赖**：「最稳」≠「必须」。关掉一条仍有另一条兜底 |
| `patchListerThingsRejectMislabeledInstrument`（源头拦截【11】） | 「与『音乐淡出每帧报错』那一项**配套，建议一起开**」 | ⚠ **是「建议」不是「必须」**：源头拦截关掉后，下游那条仍能拦住异常 |
| `xmlExtensionsFindMod`（XmlExtensions 的 FindMod 判定失效【14】） | 「走的是 XmlExtensions 自己那条代码路径（与本补丁包另一处修复**互不重叠**，**两者都要开才完整**）」 | ⚠ **唯一真正的「都要开才完整」** —— 但它描述的是「覆盖两条不同代码路径」，不是「一条依赖另一条」 |

### 17.4 结论：72 个开关**没有一个是「关掉会坏」的**

四条都读完了，最接近「依赖」的 `xmlExtensionsFindMod` 实际语义是：

- `patchModListerHasActiveModWithName`（【4】）修的是**原版** `PatchOperationFindMod`；
- `xmlExtensionsFindMod`（【14】）修的是 **XmlExtensions 自己**实现的 FindMod 判定；
- 两者作用于**不同的代码路径**，各自独立生效；「都要开才完整」说的是**覆盖率**，
  不是「一个失效另一个也不工作」。

⇒ **关掉任何一个开关，游戏行为只会退回到「该项修复没生效」这个状态，不会出现「半运行」或「更糟」**。
这是这套开关设计里最值得肯定的一点。

### 17.5 一条不影响结论但值得记的观察

`steamWorkshopHook` 与 `patchListerThingsRejectMislabeledInstrument` 的描述里用了「最稳」「建议」——
这类措辞**对用户是友好的**（说明不是硬依赖），
但也意味着**用户可能只开一个就以为「已经修好了」**。

若将来要改进：可在设置界面里给这类项加一个弱提示（如「建议与【22】同开」），
而不是靠用户读完整段描述。**本轮不动** —— 属于 UI 增强，不是缺陷。

### 17.6 这一节对界面验证的意义

界面点击验证（需要你操作）时，可以**只重点验 4 个开关**：`allDiagnostics`、
`steamWorkshopHook`、`patchListerThingsRejectMislabeledInstrument`、`xmlExtensionsFindMod` ——
其余 68 个关掉的后果都是「该项修复没生效」，从日志就能判断，不需要逐个点。

⚠ 判据局限：本节只做**静态语义分析**（读描述），不是实测。

### 24.4 第 2 条的注释里有一段很重要的历史（作者早就踩过这个坑）

`RJW17_SraeLibFieldCleanup.xml` 的注释写着：

作者当时的处置是**再加一道目标守卫 + `success=Always`**，而不是继续信赖版本守卫。

## 25. 第十九轮追加（R381）：NMM 两条正文通道**逐条对齐**，100% 一致

### 25.1 为什么要比

NMM 的正文走两条完全不同的通道：

| 通道 | 用于 | 形态 |
|---|---|---|
| `OwnInjections\…\*.xml` | **1.6**（DLL 运行时直改 `List<string>`） | `<defName>.opinionTexts` + N 个 `<li>` |
| `v1.7\Languages\…\Keyed\` | **1.7**（`OpinionTextTranslator` 拼 Keyed 键） | `<NMM.Opinion.<defName>.opinionTexts.<i>>` 逐条 |

**若同一个 def 在两处译文不同 → 同一场景在 1.6 与 1.7 下读出不同文字。**
这一项之前没查过。

### 25.2 第一次比对：0 个共同 def（我找错目录了）

第一版把 1.7 通道找成 `v1.7/…/DefInjected/` —— 那里只有 **1,190 键 / 72 def**（label、Hediff、Trait 之类）。
而 1.7 的**正文**其实在 `Keyed/`：`PrivateParts.01~24.xml` + `Generator.01.xml` + `Situational.01~02.xml`。

**改正后**：1.6 通道 5,214 个 def、1.7 通道 5,154 个 def、**两处都有 5,082 个**。

### 25.3 第二版比对：115,353 条「不同」

第一版逐条比 `1.7[i] == 1.6[i]`，结果 **相同 7,668 / 不同 115,353**。
抽样看：

```
Opinion_Anus_Negative_Abyssal
  1.6 [0] = 不合我的口味。
  1.7 [0] = 就这样，还有什么好说的？    ← 这是父模板 BaseSexPartOpinionDef 的兜底句
  1.7 [1] = 不合我的口味。              ← 与 1.6 的 [0] 相同
```

⇒ 不是译文不同，是**索引起点不同**：1.7 的键**必须**把父模板那条算进索引 0，否则就是错位。

### 25.4 第三版：按「有无父模板」分组，两边都 100%

| 分组 | def 数 | 判据 | 成立 | 不成立 |
|---|---|---|---|---|
| **A：1.7 比 1.6 多 1 条**（有父模板） | **4,509** | `1.7[i+1] == 1.6[i]` | **115,353** | **0** |
| **B：两边条数相同**（无父模板） | **573** | `1.7[i] == 1.6[i]` | **7,668** | **0** |

**两组都是 100%，合计 123,021 条逐条对齐，零不一致。**

### 25.5 这个结果同时验证了 v1.5.1 那次「错位一位」的修复是完整的

`README` 里 v1.5.1 那条写着：
> 627 个「情境看法」的正文全部错位一位……现已逐个前移复位（16,200 条键重排，两份语言目录同步）

当时修的是 **Situational**（情境）。而这次验证覆盖的是 **SexPart**（身体部位看法）那 5,082 个 def ——
它们分成两类、**两类都对**：

- 4,509 个有父模板 → 1.7 索引 0 放父兜底句，子内容从 1 开始（**正确偏移**，不是 bug）；
- 573 个无父模板 → 1.7 与 1.6 索引一一对应。

⇒ **错位问题在两条通道上都已经解决，没有残留。**
