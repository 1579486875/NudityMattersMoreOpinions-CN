## 一、总纲

**审计脚本报「不通过」时，先怀疑脚本，再怀疑数据。**

这条规则在本次审查中被违反过 12 次，每一次的代价都是：
先按错误结论动了一轮手，发现不对，回滚，再重来。

**更硬的一条**（本次新增）：

> **「exit 0」不是结论，「有判据的 exit 0」才是。**
> 一个永远 `sys.exit(0)` 的脚本，跑一万次「通过」也只说明它没崩。

## 二、23 种形态

### 类别 A：注释检测（模板 §3.2.4 的适用范围）

| # | 形态 | 错误表现 | 正确判据 | 模板是否覆盖 |
|---|---|---|---|---|
| A1 | 只认 `///`，不认 `//` | 154 条「缺注释」，实际全有 | `//` 与 `///` **都算**注释 | ✅ 已覆盖（§3.2.4 第 1 条） |
| A2 | 只往上看固定 8~140 字符 | 长注释块 + 空行后就被判缺 | 向上找到**最近的非空行** | ✅ 已覆盖（同理） |
| A3 | **属性行挡住注释** | `/// <summary>` 下面隔一行 `[StaticConstructorOnStartup]`，就被判缺 | 向上找时**跳过** `[` 开头的属性行、`#region`、`#if` | ❌ **未覆盖** |
| A4 | **只看上方、不看行尾** | `private const float X = 510f; // 说明` 被判缺 | 同一行的 `//` **也算**注释 | ❌ **未覆盖** |
| A5 | **一条注释覆盖连续多个字段时漏判** | 注释块下面有 4 个字段，第 2~4 个被判缺 | 遇到同类字段声明时**继续往上找**，不就此判定 | ❌ **未覆盖** |
| A6 | **调用语句被当成方法声明** | 正则 `\w+\s*\(` 匹配到 `ApplyAll();` → 注释被插到**调用点**上方 | 声明行**不可能以 `;` 结尾**（本仓无抽象/接口方法） | ❌ **未覆盖（最危险）** |
| A7 | 控制流关键字被当成方法 | `if (`/`for (`/`catch (` 被当成方法声明 | 排除 `if/for/foreach/while/switch/catch/using/return/throw/new/await/yield/lock` 等 | ✅ 已覆盖（§3.2.4 第 2 条） |

**A6 为什么最危险**：它不会报错，只是把注释插到**看起来合理但完全错误的位置**。
编译能过、XML 能过、连格式检查都过 —— 只有人读代码时才会发现「这段注释在讲一个没被定义的东西」。

### 类别 D：字面量匹配

| # | 形态 | 错误表现 | 正确判据 |
|---|---|---|---|
| D1 | **Python 里替换反斜杠字面量双写** | `r"About\\About.xml"` 与文件里的 `r"About\About.xml"` 不匹配 → `in` 判断恒假 | 用**行级替换**（按行号定位），或 `chr(92)` 拼 |

## 三、对照模板 §3.2.4 的覆盖度

| 模板列的六种 | 本清单对应 |
|---|---|
| ① `//` 与 `///` 都算注释 | A1 |
| ② 控制流关键字不是方法 | A7 |
| ③ lambda / 局部函数 | —（本次未踩到） |
| ④ 接口实现 | —（本次未踩到） |
| ⑤ 自动属性 | —（本次未踩到） |
| ⑥ record / init 访问器 | —（本次未踩到） |

**模板缺的三条**（本次都真踩了）：

1. **A3 属性行挡住注释** —— 这是 C# 里极常见的形态（`[StaticConstructorOnStartup] public static class X`），
   不加「跳过属性行」的判据，所有带特性的类/方法都会被误报「缺注释」。
2. **A4 行尾注释** —— 短常量、短字段几乎都写成行尾注释，不认它就等于把那部分全判成缺失。
3. **A6 调用语句被当成声明** —— 危害最大：它不报错，只把注释插到错误位置，**任何自动检查都发现不了**。

**建议**：把这三条补进模板 §3.2.4 的误报清单；并把「**声明行不可能以 `;` 结尾**」写成硬判据。

### 类别 G：批量文本替换（2026-11-16 新增，R383 实证）

| # | 形态 | 错误表现 | 正确判据 |
|---|---|---|---|
| G1 | **批量替换同义词，没扫「目标词与替换词同句共存」** | 把「突然一瞥X的**胸部**，露出的**乳房**显然已不复当年」改成「…的**乳房**，露出的**乳房**…」，把好句子改坏 | 替换前先扫一遍：**若句内或同段已存在替换词，说明原文用那个词可能正是为了避重复** —— 这一类必须逐条看 |

**为什么归到这一类而不是 F（语义口径）**：F 是「拿两个不同量纲的数比」，G 是「机械替换破坏语义」，
两者的错法不同 —— F 错在**判据设计**，G 错在**缺少前置扫描**。

**实证出处**：报告第 27 节（R383）。那次 dry-run 扫出 3,700 处，抽看前 6 条就发现 2 处会改出病句，
于是整批放弃 —— 这是本轮**唯一一次「分析完主动不做」**的记录。

## 四、可执行的预防清单（下次审查照做）

跑任何「扫描/审计」脚本之前：

- [ ] 这个脚本**失败时会 exit 非 0 吗**？（先故意破坏一次验证，别信代码阅读）
- [ ] 它扫的路径是**从 `__file__` 推导**的还是硬编码的？本机有几个同名 clone？
- [ ] 它比的是**键集合**还是文件集合？是**C# 类型**还是 XML 实例？
- [ ] 它的正则/字面量**容忍换行、缩进、行尾注释、属性行**了吗？
- [ ] 它的「问题变量」名字叫什么？我破坏的是它读的那个吗？
- [ ] 它报出的数字，**口径**与我拿来比较的那个数字一致吗？
- [ ] 改完文件后，`git status` 干净吗？字节与原样一致吗？
