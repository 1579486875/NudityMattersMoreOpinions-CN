# Bug report — the Opinions tab disappears for "artificial" races

**Target mod:** `Nudity Matters More opinions`
**Package ID:** `shark510.nuditymattersmoreopinions`
**Upstream repo:** https://github.com/MiruKoto/NudityMattersMore_opinions
**Verified version:** Manifest `1.0.9` (the reporter in the field was on `1.0.0` and saw the same thing)
**Environment:** RimWorld 1.7.5011.24; also reproducible in structure on 1.6.4871
**Hard dependency in play:** `rim.job.world` (RimJobWorld)

---

## 1. Summary

`ITab_Pawn_NMMOpinions.IsVisible` gates the tab on `rjw.xxx.can_do_loving(pawn)`.

For any **humanlike** race whose `FleshType.defName` contains `"Android"`, RJW's
`is_mechanoid()` returns `true`, so `can_do_loving()` returns `false` on its **very
first line** and the tab never appears — while every other feature of this mod keeps
working normally.

In other words: the nudity-things work, only the tab is gone. That mismatch is what
made this hard to notice upstream.

---

## 2. Reproduction

1. Install RimJobWorld + Nudity Matters More + Nudity Matters More *opinions*.
2. Install **any** race mod whose `FleshType` defName contains `Android`
   (many "artificial" / android-style race mods do; the mod in question does).
3. Spawn or recruit a pawn of that race and select it.
4. Vanilla humans show the tab (`… | 裸体 | …`); that race does not.
5. **Changing the pawn's age changes nothing** — a 16-year-old and a 20-year-old of
   that race both lack the tab.
6. But the mod's own mechanics are fine: nudity is still covered, streaking still
   applies a mood penalty, opinion texts still generate.

Step 5 is the important one: it rules out "underage" and points at a race-wide gate.

---

## 3. Root cause (decompiled, 1.7.5011)

`NudityMattersMore_opinions.ITab_Pawn_NMMOpinions.IsVisible` has exactly three terms:

```csharp
return canDoLoving && isHuman && !isEntityOrGhoul;
```

| term | implementation | for such a race |
|---|---|---|
| `isHuman` | `pawn.def.race.Humanlike` → `RaceProperties.Humanlike => (int)intelligence >= 2` | `true` (inherits Human) |
| `isEntityOrGhoul` | `if (!pawn.IsEntity) return pawn.kindDef == PawnKindDefOf.Ghoul;` | `false`, so `!…` is `true` |
| `canDoLoving` | `rjw.xxx.can_do_loving(pawn)` | **`false`** ← the problem |

`rjw.xxx.can_do_loving` starts with:

```csharp
public static bool can_do_loving(Pawn pawn)
{
    if (is_mechanoid(pawn)) return false;   // <-- never gets past this
    if (is_human(pawn)) { … age checks … }
    …
}
```

And `rjw.xxx.is_mechanoid` decides "mechanoid" by **string containment**:

```csharp
public static bool is_mechanoid(Pawn pawn)
{
    if (pawn == null) return false;
    if (AndroidsCompatibility.IsAndroid(pawn)) return false;          // ← the only exemption
    return pawn.RaceProps.IsMechanoid
        || pawn.RaceProps.FleshType == FleshTypeDefOf.Mechanoid
        || pawn.RaceProps.FleshType.corpseCategory.ToString().Contains("CorpsesMechanoid")
        || pawn.RaceProps.FleshType.defName.Contains("GR_Mechanoid")
        || pawn.RaceProps.FleshType.defName.Contains("MechanisedInfantry")
        || pawn.RaceProps.FleshType.defName.Contains("Android");      // ← name contains "Android"
}
```

The exemption is hard-wired to a single mod's extension type:

```csharp
// rjw.AndroidsCompatibility static constructor
typeName = "Androids.SexualizeAndroidRJW";
```

**Conclusion:** apart from `Androids` itself, any race whose `FleshType` defName
contains `"Android"` is classified as a mechanoid → `can_do_loving` returns `false`
→ the tab is hidden. The mod's own nudity logic never consults `is_mechanoid`, which
is exactly why everything else still works.

---

## 4. Suggested fix (your side)

**The tab's visibility should not depend on whether the pawn is able to have sex.**
Those are unrelated concepts, and tying them to RJW also makes this mod break whenever
RJW changes (or is absent — see §6).

Minimal change:

```csharp
// drop the can_do_loving term
return isHuman && !isEntityOrGhoul;
```

If the `can_do_loving` gate was there to keep minors out, gate on age directly instead
of going through RJW:

```csharp
bool adult = pawn.ageTracker.CurLifeStage.reproductive
             || pawn.ageTracker.Growth >= 1f;
return adult && isHuman && !isEntityOrGhoul;
```

Either way the dependency on `rjw.xxx.is_mechanoid` — and therefore on its string
matching — disappears.

## 5. Workaround currently shipping (for your reference only)

Our Simplified-Chinese localization pack ships a Harmony **postfix** on
`get_IsVisible` that flips the result back to `true` **only** when all of these hold:

1. `pawn != null`
2. `pawn.def.race.Humanlike`
3. `!NudityMattersMore.InfoHelper.EntityOrGhoul(pawn)`
4. `rjw.xxx.is_mechanoid(pawn) == true`  ← i.e. it really is the misjudgement above

Because of condition 4, minors of a humanlike race still get no tab, real mechanoids
are excluded by condition 2, ghouls/entities by condition 3, and vanilla humans are
unaffected (their `IsVisible` already returns `true`, so the postfix returns early).

This is offered as evidence and as a stopgap — **not** as a substitute for fixing the
visibility logic upstream.

## 6. Two additional observations that may matter to you

**6.1 The same gate breaks the tab when RJW is missing.**
`IsVisible` calls `rjw.xxx.can_do_loving(...)` unconditionally. If RJW is absent or its
assembly changes, the getter fails at JIT time and the tab disappears **for every race**,
vanilla humans included. Since `rim.job.world` is already a hard dependency this is
probably acceptable, but it makes the failure mode very confusing to end users.

**6.2 A different mod makes the same mistake, with a visible side effect.**
`ElToro.MAddon` (`ElToro.MAddon`) uses the identical call:

```csharp
// ElToro_MAddon.MCPTargetGrantUtility.TryGrant
if (p != null && !p.Dead
    && p.Faction == Faction.OfPlayer
    && xxx.is_mechanoid(p)
    && defs.SubcoreBioprinting_RP.IsFinished)
{
    p.abilities.GainAbility(defs.MCPTarget);   // "植入生物打印机" / implant bioprinter
}
```

So a misjudged race **silently gains the bioprinter ability** while losing our tab.
That also gives a zero-cost way to confirm the diagnosis in the field: select the pawn
and check whether it has that ability. If it does, `is_mechanoid` is definitely `true`.

You may want to pass 6.2 along to that author as well.
